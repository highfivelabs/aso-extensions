`docs/coverage/` on `main` at `55b95a4`. The builder, 2026-11-11: "I would
have expected the machinery to generate code here to get further along."

## Why

1. **The queue stopped, not the generator.** For 23 hours no agent built a
   kind, and merging moved from the authoring agent to a person when CI
   arrived (#37, 2026-11-10 07:08): the wait per pull request went from
   minutes to a day. Every waiting pull request then needs `main` merged in
   and its generated files regenerated (a heavy run) each time another
   lands, because every kind pull request edits the same files:
   `pkg/controllers/arm_resources_gen.go`, `config/crds/kustomization.yaml`,
   `generator/reports/`, `docs/coverage/`, the README's coverage section,
   `tests/operator/run.sh`, `required-ok.txt`, the fake's dispatch in
   `pkg/fakecloud/arm/arm.go`, and three docs. #40 to #46 each carry one or
   two "Merge main into ..." commits with regenerated output. Merging is
   serial; the queue grows behind it.
2. **The hand-written part of a kind is 90% tests and fakes.** The rule was
   that every kind gets its own fake rules, envtest and kind run before it
   merges. Those are 4 to 9 times the lines of the generator
   configuration that actually makes the kind, and they are what a session
   spends its time on.
3. **A generator iteration costs a machine run, and a person between
   runs.** The generator reports missing labels a batch at a time, and each
   round trip was a run, read by the agent, a fix, and another run. On the
   Ubuntu machine (lent out on 2026-11-10) a run took 30 seconds; on an
   offload Spot VM with its cache it takes about 2 minutes (VM up 77 to 130
   seconds, measured 2026-11-11), so the cost is the round trips, not the
   machine: a new group took 3 to 6 of them.
4. **Rows are small.** One foundation row (1 to 7 kinds) per pull request
   pays the fixed cost (docs in five places, a coverage regeneration, CI, a
   merge) for few kinds. A resource provider is one configuration file and
   could be one pull request.

## Fixes

Done in this change:

- **Every generated kind is tested without writing a test**
  (`test/e2e/arm_conformance_test.go`, `docs/testing.md`, layer 1): the
  smallest object the CRD accepts, owned through a parent chain derived
  from the kind's ARM type, must become Ready, appear in the fake at the
  right ID and type, take a change and delete. A new kind merges with this
  test alone (plus a fixture line when the fake asks for more); kind tests
  and fake rules are written for kinds with behaviour of their own, over
  time.
- **One machine run does every generator iteration**
  (`hack/generate-iterate.sh`, `hack/autolabel`): the generator runs until
  it passes, writing the reference labels it asks for between runs
  (`$referenceType: arm` for a property named as an ARM ID, `simple`
  otherwise, each marked `autolabel: review`). Errors autolabel cannot fix
  stop the loop with the log.
- **Merging is the authoring agent's again** (the builder, 2026-11-11):
  merge once CI is green, then rebase the next.

Then: **a pull request per resource provider**, several API versions in one
group file (Defender for Cloud first: `generator/azure-arm/security.yaml`).

Recommended, not done here (each touches files the open queue edits):

- Regenerate `docs/coverage/` and the README's coverage section on `main`
  after a merge (a nightly job) instead of in every pull request: it is
  the commonest conflict and is not checked in CI.
- Register the fake's per-area rules from each file (`init`) instead of a
  dispatch list in `arm.go`.
- Let `tests/operator/run.sh` take one kind per group by default and leave
  the rest to conformance.

## After the fix (2026-11-11, the same day)

| | Before | After |
| --- | --- | --- |
| Kinds per pull request | 1 to 7 (median 4), one foundation row | 11 to 12, a resource provider or a theme (#58, #59, #60) |
| Machine runs per group | 3 to 6, a person between each | 1 to 3 (autolabel writes the labels; the rest were enum names, recursion and polymorphism, each a known fix) |
| Machine run | 30 s on the Ubuntu machine (gone) | about 2 minutes on a Spot VM with the cache |
| Hand-written lines per kind to merge | 150 to 500 (fake rules, envtest, kind run) | 0 to 10 (a conformance fixture when the fake asks) |
| Kinds generated in the session | | 35 (Defender for Cloud 12, Sentinel 11, governance 12) in about four hours, beside the fix |
| Wall clock per batch | | 30 to 60 minutes from configuration to `task check` passing |

What still costs time: errors the generator reports one at a time
(recursion, enum names in the storage version, a property named `Owner`),
each a round trip; four of them took two to four runs. A pre-check that
lists a spec's recursive properties and enum-valued names before the first
run would save most of those. Merging is the remaining wait: CI could not
run on 2026-11-11 (GitHub Actions refused jobs for billing), so the
pull requests carry a `task check` run on an offload VM instead and wait
for CI.
