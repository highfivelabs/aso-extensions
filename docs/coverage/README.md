# Coverage of the Azure Resource Manager API

How much of the Azure API Azure Service Operator v2 (ASO, "official") covers,
how much more our kinds cover ("ours beyond official"), and how much neither
does ("uncovered"), by service, by resource and by attribute. The bars in the
[root README](../../README.md#coverage) are made from these files.

The tool is [`hack/coverage/`](../../hack/coverage); everything here except
this file's prose, `priority.csv` and `sources.yaml` is generated by it and
checked by `hack/coverage/run.sh --check`.

| `attributes.csv` | attribute | `service,resource,attribute,type,required,covered_by,official_path,ours_path` |

| `priority.csv` | service the builder ranks | `service,tier,rationale,source` (hand-edited) |

The first three files have the same columns in the Google Cloud and AWS
repositories. `tiers.csv` and `priority.csv` are additions. Percentages are of
`attributes_total`, to one decimal. `covered_by` is `official`, `ours`, `both`
or `none`. Kinds are `;`-separated `group/Kind`. `notes` is `;`-separated
`key=value` tokens and flags: `spec_api` (the API version of the
denominator), `official_api` and `ours_api` (the version the kind speaks),
`official-api-differs-from-spec`, `spec-preview-only`,
`not-in-latest-spec-version`, `outside-denominator`, `unmapped=...`.

## Definitions

- **service**: an Azure resource provider, the namespace in the ARM path
  (`Microsoft.Network`, `Microsoft.KeyVault`).
- **resource**: one ARM resource type under a service
  (`Microsoft.Network/virtualNetworks/subnets`): a path in the OpenAPI specs
  with a PUT that creates a top-level or nested resource.
- **attribute**: a writable property path of the resource's PUT request body,
  with `[]` for arrays and `{}` for maps, so `properties.ipConfigurations[].properties.subnet.id`.
  It includes top-level writable fields (`location`, `tags{}`, `sku.name`,
  `identity.type`, `kind`, `zones[]`). A leaf is counted, not each object on
  the way: an object with nothing writable below it (a free-form object, or a
  map whose values have only read-only properties, like
  `identity.userAssignedIdentities{}`) is itself one leaf.
  **Read-only properties are excluded**: a property is read-only when the spec
  says `readOnly: true` (on the property or on the definition it points to), or
  `x-ms-mutability` allows neither `create` nor `update`. The envelope
  fields `id`, `name`, `type` and `systemData` are not attributes (the name is
  in the path). `required` is true when the property is required in its
  object and every object above it is required too.
- **official**: ASO v2 at the pinned commit has a kind for the resource and its
  CRD spec has a property for the attribute.
- **ours**: a kind in this repository's CRDs covers the attribute. "Ours beyond
  official" is an attribute (`covered_by=ours`) or a whole resource
  (`resources_ours_beyond`: ours has a kind, official has none) that only ours
  covers. `ours_from_upstream_pr` is true when ours is copied from an unreleased
  upstream pull request or `main`; none are at present.
- **uncovered**: in the API, in neither.

## Method

**Denominator: the specs.** The OpenAPI files of `Azure/azure-rest-api-specs`,
`specification/*/resource-manager`, at the commit ASO's own submodule pins
(`sources.yaml`), so ASO and the denominator read the same specs; fetched as a
blob-less depth-1 fetch of just the files needed (about 100 MB; the repository
is several GB). A spec set is a folder of versions (`.../Microsoft.X/<Project>/stable/<version>/`).
Versions were chosen per *file*: each file name is read at the latest stable
version that has it, or if none is stable at its latest preview. A provider's
latest version is not enough: in some sets (Monitor's) a version folder holds
only the files that changed in it, so the latest folder alone misses most of the
provider's resources. For a snapshot-style set this reads the latest version
only. When a resource is in several files or versions, the highest version
wins (stable over any preview) and the attributes of one version are merged.

A PUT path is a resource when, after the last `/providers/<namespace>/`, it has
type/name pairs: `.../virtualNetworks/{name}/subnets/{name}` is
`Microsoft.Network/virtualNetworks/subnets`; a literal name (`.../blobServices/default`)
is a resource; an action (`.../start`) or a list is not. A type segment that is
a path parameter with an enum (`{recordType}` for DNS records) is one resource
per value. A resource group has no provider in its path and is special-cased. A PUT
without a body is a resource with no attributes. Attributes are the
leaves of the body schema, following `$ref` across files, merging `allOf`, and
taking a discriminated union as every subtype's properties at the union's path
(`discriminator` plus the definitions that extend it). A recursive reference
stops at its first repeat and is one leaf of type `object`.

**Official: ASO's API types.** At the ASO commit, each API version of each
group has an `arm` package (the wire types, with `GetType()` naming the ARM
type and `GetAPIVersion()` its version) and an API package (the Go types the
CRDs are generated from). A kind's ARM type comes from the first; what a user
can set comes from the second's `<Kind>_Spec`, minus `azureName`, `owner` and
`operatorSpec`, which are the operator's. Per ARM type the version used is the
newest stable one ASO has (preview only if none is stable). The ARM wire types
alone overstate: ASO keeps embedded children in the wire type that its CRD does
not have (`VirtualNetwork.subnets`, `NetworkSecurityGroup.securityRules`;
those are separate kinds), so the CRD's types decide.

**Ours.** Generated kinds (`apis/arm`, written by ASO's generator) are read the
same way. Hand-written kinds are read from their CRDs and
`hack/coverage/ours.yaml`, which maps each CRD spec path to the ARM attribute it
sets; the tool fails if a CRD property is neither mapped nor ignored, and if a
CRD in `config/crds` is neither generated nor listed there. Kinds that are not
ARM resources (Key Vault data-plane secrets and certificates, PostgreSQL
roles) have rows with `notes=outside-denominator` and are in no percentage.

**The join.** An attribute is covered by a kind when the kind's CRD spec has a
property at the same path, compared without case, where ASO's changes to the
spec's shape are undone:

- the `properties` bag is flattened, to any depth: `properties.a.properties.b`
  is looked up with any of its `properties` segments removed;
- a property that holds a resource ID is `xReference` (or `x.reference` inside
  a `{reference}` struct) and is entered under the ARM name from its
  `armReference` tag (`subnet.id`, `userAssignedIdentityId`), and for a name
  without a tag under the field's name minus `Reference` with `Id`, `ResourceId`
  and similar added; a map of references keyed by ID
  (`identity.userAssignedIdentities{}`) is an array of `{reference}`;
- a union's variants are at the union's own path (ASO wraps each in a field
  named for the discriminator value, so `backupPolicy.continuous.x` is
  `backupPolicy.x`); a struct is a union when its fields are documented
  "Mutually exclusive with all other properties";
- a CRD leaf that takes any JSON covers every attribute below it, and a CRD
  property that is an object covers a spec leaf of the same path whose detail
  it models;
- `xFromConfig` is `x`.

**Version lag.** ASO often lags the latest API version. Each ASO kind is
compared with the denominator at the ASO version's own schema: an attribute
that only the newer version has is uncovered, an ASO property the newer version
no longer has is ignored. `notes` has `official_api` and `spec_api` and the flag
`official-api-differs-from-spec` when they differ. That makes `pct_uncovered`
partly "ASO has not moved to the new API version", which is a real gap for
someone who needs the new property, and not the same as ASO lacking the
resource.

**Tiers.** Not every service matters alike, so `priority.csv` ranks them, by
hand. Tier 1 is the resource providers used by the foundational modules people
migrate first, the top ten Azure Verified Modules by yearly registry downloads
(virtual network, network security group, storage account, Key Vault, virtual
machine, resource group, managed identity, Log Analytics workspace, route table,
NAT gateway) and the providers of the shared interfaces nearly every module
takes (role assignments and locks: `Microsoft.Authorization`). Tier 2 is every
other provider that a tracked module uses or that the ranking names as a gap.
Tier 3 is everything else, and the default for a service missing from the file.
The ranking is `highfivelabs/catalog docs/azure.md` (sections 2, 4 and 5), read
2026-11-09; each row names its rank in `rationale` and `source`. The builder
may change any row; the generator reads the file and never recomputes it, and
fails if a row names a service that is not in `services.csv`. The limits: usage
by modules is a proxy for what teams need, taken from one registry, at one
date, and counting a module once however many resources it creates; a team's
real list differs; a provider is one unit though its resources matter very
unequally (`Microsoft.Network` has virtual networks and also ExpressRoute and
Virtual WAN); and tier 3 holds hundreds of providers, many third-party
(`Anyscale.Platform`, `Dell.Storage`) or preview-only (`Microsoft.AwsConnector`),
so its low figure says little. A tier's percentage moves with its biggest
member.

## Known error and caveats

- **The specs are those at ASO's pin (2026-10-22)**, not the newest; an API
  version published since is not in the denominator.
- **Counts are of leaf attributes**, so a resource with large nested arrays
  (an application gateway has 266) weighs more than a small one, and one service
  can dominate the total: see the note on `bars/_total.svg`. Attributes the spec
  does not mark read-only but the service sets (`properties.provisioningState`
  and `properties.vaultUri` in the Key Vault spec) count as writable.
- **Legacy and preview.** Old spec sets (the 2017 `Microsoft.ContainerService`
  orchestrators, classic resources) and preview-only providers are in the
  denominator; the count is in the numbers below. Excluding them would raise
  every percentage.
- **Covered means a property exists**, not that the controller handles it well
  (long-running operations, secrets, ordering). It is a measure of schema, not
  of quality.
- **Matching can miss.** A property ASO renamed without an `armReference` tag,
  or one whose flattened name collides with another, is counted uncovered. The
  spot checks found none among 1,257 attributes, but they cover 18 of 299
  resources.
- **Several ASO kinds for one ARM type** (a kind renamed across versions) are
  reduced to one, the newest stable.
- **`type`** is empty on outside-denominator rows. `official_path` is the path
  in ASO's API type (the CRD spec path), `ours_path` the same for ours, or
  `spec.<path>` for a hand-mapped kind.
- The generated kinds of the Container Apps environment children are in once
  they are merged and the tool is rerun; the figures here are for what is on
  `main`.

## Spot checks

Run 2026-11-09 against the real CRDs of ASO v2.22.0 (the nearest release; the
pin is 16 commits ahead, so only resources and versions both have were
compared): `hack/coverage/run.sh --spotcheck <crds.yaml>` compares, for
18 resources across 13 providers (`Microsoft.Network` virtual networks, subnets,
network security groups, public IPs and DNS A record sets; compute virtual
machines and disks; AKS managed clusters; storage accounts; Key Vault; PostgreSQL
flexible servers; SQL servers; Cosmos DB accounts; Service Bus queues; Event Hubs
namespaces; managed identities; role assignments; App Service plans), whether
each attribute of the denominator is covered according to this tool and
whether the CRD spec has a property for it. **1,239 of 1,257 attributes
agree (98.6%).** The 18 that differ are all limits of the spot check's own,
simpler reading of the CRD, not of the tool: `identity.userAssignedIdentities{}`
(the CRD has it as an array of references), eight Cosmos DB `backupPolicy.*`
properties (the CRD wraps each union variant), and
`networkAclBypassResourceIds[]` and similar reference arrays, which are in the
CRD under `...References`. The earlier version of the tool, which read the ARM
wire types instead, disagreed on 41% of virtual network and 65% of network
security group attributes (embedded children ASO leaves out of the CRD); that
is why the API types are used.

The denominator was re-derived for five resources with a separate, simple
reader of the swagger (Key Vault `vaults`, and network `virtualNetworks`,
`loadBalancers`, `applicationGateways`, `azureFirewalls`): the attribute
sets are identical.

## Regenerating

```sh
hack/coverage/run.sh            # regenerate docs/coverage/ and the README's Coverage section
hack/coverage/run.sh --check    # fail if what is committed differs (no timestamps; deterministic)
hack/coverage/run.sh --test     # the tool's unit tests
hack/coverage/run.sh --spotcheck .cache/spotcheck/azureserviceoperator_customresourcedefinitions_v2.22.0.yaml
```

The first run fetches the two pinned commits into `.cache/coverage/`
(gitignored), a few minutes; later runs take seconds. To move a pin, change
`sources.yaml` (and `UPSTREAM.md` for ASO) and rerun. To change a tier, edit
`priority.csv` and rerun. `task coverage` runs the first and `task coverage-check` the second.
